# 00. 기획 로드맵

관리자 서비스 기획 문서의 작성 순서와 확정된 전제를 정리한 문서다.
각 문서는 초안 작성 → 검토·수정 → 확정 순서로 진행하며, 확정되면 상태를 갱신한다.

## 1. 프로젝트 개요

- 사용자 서비스(개인·기업 회원 대상)를 운영하기 위한 **관리자 서비스**를 만든다.
- 사용자 서비스 자체는 이번 범위에 포함하지 않는다.
- 학습 목적으로 하나의 백엔드에 **프론트엔드 3종**을 함께 구현한다.

### 기능 목록

| No | 기능 | 비고 |
|---|---|---|
| 1 | 기업정보관리 | 기업 회원이 소속된 기업 정보 |
| 2 | 사용자관리 | 개인 회원, 기업 회원 |
| 3 | 메뉴 동적관리 | 관리자 화면의 메뉴 트리를 DB로 관리 |
| 4 | 코드관리 | 그룹코드 / 상세코드 |
| 5 | 통합게시판관리 | 게시판 유형을 설정으로 생성 |
| 6 | 관리자관리 | 관리자 계정 |
| 7 | 관리자 권한관리 | 메뉴 × 액션 단위 권한 |
| 8 | 관리자 역할관리 | 권한의 묶음 |

## 2. 확정된 전제

| 항목 | 결정 내용 |
|---|---|
| 사용 주체 | 내부 운영자만 로그인한다. 기업 담당자는 로그인하지 않으므로 멀티테넌트 구조는 필요 없다. 데이터 범위 권한(특정 기업만 관리)도 두지 않는다. |
| 접근제어 | RBAC. 관리자 →(N) 역할 →(N) 권한, **권한 = 메뉴 × 액션** |
| 백엔드 | 전자정부프레임워크(eGovFrame) 5.0.2 (Spring Boot 3 계열, Java 17 이상). 서버 애플리케이션 1개로 API·세 프론트 화면·배치를 모두 제공 |
| UI | 세 프론트 모두 Bootstrap 5 + Tabler 테마. 에디터 Quill, 우편번호 카카오 우편번호 서비스 |
| DB | PostgreSQL |
| 인증 | 학습 목적으로 두 방식 모두 구현. ① React, ② JSP + API는 토큰(JWT), ③ JSP SSR은 세션 |
| 프론트엔드 | ① React + REST API ② JSP + REST API(AJAX) ③ JSP 서버 렌더링(Spring MVC) |
| 통합게시판 범위 | 게시판 설정(게시판 생성·옵션 관리)과 게시글 운영(공지 작성, QnA 답변, 게시글·댓글 삭제 등)을 모두 포함한다. |
| 기획 문서 | 저장소 `docs/` 아래 Markdown으로 작성하고 git으로 관리한다. |

### 프론트엔드 3종을 고려한 설계 원칙

- 비즈니스 로직은 **Service 계층 하나**에 둔다. 그 위에 진입점을 두 가지 둔다.
  - `@RestController`: ①, ②가 호출하는 REST API
  - `@Controller`: ③이 사용하는 JSP 뷰
- ③ JSP SSR은 **REST API를 호출하지 않는다.** `@Controller`가 Service를 직접 호출하고, 결과를 Model에 담아 JSP로 렌더링한다. 구체적인 구현 방식은 08 아키텍처 문서에서 정한다.
- **화면 명세와 API 명세를 분리**해서 작성한다.
  - 화면 명세는 프론트 종류와 상관없이 1벌만 작성하고, 3개 프론트가 같은 명세를 구현한다.
  - API 명세는 ①, ②가 공통으로 사용한다. ③은 API 명세 대신 화면 명세와 Service를 기준으로 구현한다.
- 권한 체크는 **서버에서 공통 처리**한다(인터셉터/AOP). 프론트는 메뉴와 버튼의 노출 여부만 제어한다.

## 4. 기능별로 결정할 사항

각 항목은 해당 기능 명세(4단계)에서 확정한다.

- **기업정보 ↔ 기업회원**: 기업 1 : N 기업회원. 승인 절차 없음, 소속 회원이 있으면 삭제 불가 (확정)
- **사용자관리**: 회원 상태(정상/휴면/정지/탈퇴), 정지·탈퇴 사유 이력, 개인정보 마스킹과 열람 로그
- **메뉴 동적관리**: 트리 깊이, 정렬, 노출 여부, URL 매핑, 메뉴 등록 시 권한 자동 생성 여부
- **코드관리**: 그룹코드-상세코드 2단계 구조, 코드 변경 시 캐시 갱신 방식
- **통합게시판**: 게시판 유형(공지/FAQ/QnA/1:1문의 등), 게시판별 옵션(댓글·첨부·비밀글·답글). 사용자 서비스에도 노출, QnA는 답글·재답글 계층형 구조이며 답글은 원글 작성자와 관리자만 가능, 깊이 제한 없음, 답글 달린 글은 삭제 표시만 하고 답글 유지 (확정)
- **관리자/역할/권한**: [02-access-model.md](02-access-model.md)에서 다룬다.

## 5. 검증 방법

- **추적표**: 8개 기능이 기능 명세, 화면 명세, API 명세, ERD, 권한 매트릭스에 빠짐없이 들어갔는지 단계마다 확인한다.
- **화면 명세 검토**: 화면 명세 1건만 보고 프론트 3종(React / JSP+API / JSP SSR)을 모두 구현할 수 있는지 확인한다.
