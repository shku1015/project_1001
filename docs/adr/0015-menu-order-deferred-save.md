# ADR-0015. 메뉴 순서는 드래그·버튼으로 바꾸고 확정 시 저장

- 상태: 승인
- 날짜: 2026-10-04
- 관련 문서: [05-screens/03-menu.md](../05-screens/03-menu.md), [06-api/03-menu.md](../06-api/03-menu.md) API-MNU-07

## 맥락

처음 화면 명세에서는 메뉴 순서를 ▲▼ 버튼으로만 바꾸고 누를 때마다 바로 저장하도록 했다. 이유는 세 프론트를 같게 만들기 쉽고(특히 ③), 드래그가 "순서 변경"과 "다른 폴더로 이동"을 섞기 때문이었다. 사용자는 **드래그와 버튼을 모두** 쓰고, **관리자가 확정할 때 저장**하도록 정했다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 버튼만, 즉시 저장 (1차 설계) | 구현 단순 | 여러 칸 옮길 때 불편. 누를 때마다 저장 |
| 드래그만 | 직관적 | 키보드 조작 불가. 다른 폴더로 떨어뜨리는 실수 |
| **드래그 + 버튼, 확정 시 저장** | 편하고, 확인 후 한 번에 저장 | 저장 전 상태 관리, 충돌 처리 필요 |

## 결정

- 드래그와 ▲▼ 버튼 모두 **같은 상위 메뉴 안에서 순서만** 바꾼다. 다른 폴더로 옮기는 것은 [상위 메뉴 변경]으로만 한다.
- 순서를 바꿔도 화면의 트리만 바뀌고, [순서 저장]을 눌러야 저장한다. [되돌리기]로 마지막 저장 상태로 돌아간다.
- 저장하지 않은 순서 변경이 있으면 메뉴 추가·이동·삭제를 막는다.
- 저장 요청에는 상위 메뉴별 하위 메뉴 목록을 빠짐없이 보내고, 현재 트리와 다르면 거부한다 (`MENU_ORDER_MISMATCH`).
- 세 프론트 모두 SortableJS를 쓴다. ③은 JavaScript로 트리를 조작한 뒤 순서 목록을 Form으로 보낸다.

## 결과

- 좋은 점: 여러 메뉴의 순서를 바꿔 보고 확인한 뒤 한 번에 저장할 수 있다.
- 감수할 점: ③ JSP SSR에도 JavaScript 상태 관리가 들어간다. 다른 관리자와 동시에 편집하면 저장이 거부될 수 있다.
