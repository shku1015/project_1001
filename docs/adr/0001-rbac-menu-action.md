# ADR-0001. 접근제어는 RBAC, 권한은 메뉴 × 액션

- 상태: 승인
- 날짜: 2026-10-04
- 관련 문서: [02-access-model.md](../02-access-model.md), [03-domain-erd.md](../03-domain-erd.md) 4절

## 맥락

관리자관리, 권한관리, 역할관리, 메뉴 동적관리 4개 기능이 서로 얽혀 있다. 다른 모든 기능이 이 구조 위에서 동작하므로 가장 먼저 정해야 했다. 사용 주체는 내부 운영자뿐이다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 권한 = 메뉴 접근만 (보임/안 보임) | 가장 단순 | 조회만 허용하고 수정은 막는 식의 구분이 안 됨 |
| **권한 = 메뉴 × 액션, 역할 = 권한 묶음** | 일반적인 RBAC. 버튼 단위까지 제어 가능 | 권한 수가 메뉴 × 액션만큼 늘어남 |
| RBAC + 데이터 범위 (특정 기업만 관리 등) | 가장 세밀함 | 모든 조회 쿼리에 범위 조건이 붙어 복잡해짐. 내부 운영자만 쓰므로 필요성이 낮음 |
| 관리자에게 권한을 직접 부여 | 예외 처리가 쉬움 | 사람마다 권한이 달라져 관리가 어려움 |

## 결정

- 관리자 →(N) 역할 →(N) 권한. **권한 = 메뉴 × 액션**(`READ`, `CREATE`, `UPDATE`, `DELETE`, `EXCEL`, `PRIVACY`).
- 권한은 역할을 통해서만 부여한다. 여러 역할의 권한은 **합집합**으로 계산하고, "거부(deny)"는 두지 않는다.
- 권한은 메뉴관리에서 메뉴의 사용 액션을 고르면 자동으로 생긴다.
- 데이터 범위 권한은 이번 범위에서 제외한다.

## 결과

- 좋은 점: 메뉴 추가가 곧 권한 추가라 운영 중에 코드 배포 없이 권한을 늘릴 수 있다. 버튼 활성·비활성까지 같은 기준으로 제어한다.
- 감수할 점: `READ` 없이 다른 액션만 있는 상태를 막기 위해 "`READ` 자동 부여·회수" 규칙이 필요하다. 권한 상향 방지(R5) 같은 보호 규칙을 따로 구현해야 한다.
