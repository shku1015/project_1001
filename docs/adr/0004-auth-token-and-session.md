# ADR-0004. 인증: ①② 토큰, ③ 세션

- 상태: 승인
- 날짜: 2026-10-04
- 관련 문서: [04-features/09-auth.md](../04-features/09-auth.md) 1.1, [07-nonfunctional.md](../07-nonfunctional.md) 1·2절

## 맥락

처음에는 "③이 세션을 쓰므로 ①②도 세션으로 맞추면 서버가 단순하다"는 제안이 있었다. 사용자는 학습 가치를 위해 세션과 토큰을 **둘 다** 구현하기로 했다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 모두 세션 | 서버 인증 방식 하나 | 토큰 방식을 학습할 수 없음 |
| ① 토큰, ②③ 세션 (1차 결정) | 프론트 구조와 인증이 자연스럽게 맞음 | 같은 화면을 다른 인증으로 비교할 수 없음 |
| **①② 토큰, ③ 세션** | ②↔③: 같은 JSP 화면을 토큰과 세션으로 비교. ①↔②: 같은 토큰을 SPA와 MPA에서 비교 | ②는 페이지를 옮길 때마다 토큰을 다시 받아야 함 |

## 결정

| 프론트 | 인증 | 보관 |
|---|---|---|
| ① React | JWT | Access Token 메모리, Refresh Token HttpOnly 쿠키 |
| ② JSP + API | JWT | Access Token 페이지 메모리, Refresh Token HttpOnly 쿠키 |
| ③ JSP SSR | 세션 | 서버 세션(DB 저장) + 세션 쿠키 |

- Access Token 30분, Refresh Token 최대 8시간. Refresh Token은 한 번 쓰면 교체하고, 재사용이 감지되면 전부 폐기한다.
- Access Token에 권한을 넣지 않는다. 권한 변경이 다음 요청부터 반영되게 하기 위해서다.
- ②는 페이지를 열 때마다 재발급 후 API를 호출한다. JSP 페이지 자체는 데이터 없는 껍데기라 서버에서 인증하지 않는다.
- Access Token을 `sessionStorage`에 두는 방식은 XSS 노출 때문에 쓰지 않는다.

## 결과

- 좋은 점: 한 프로젝트에서 두 인증 방식과 세 화면 구조의 조합을 비교할 수 있다.
- 감수할 점: 서버에 보안 설정이 두 벌(토큰, 세션+CSRF) 필요하다. 동시 로그인 금지·강제 로그아웃을 위해 세션을 DB에 저장하고(Spring Session JDBC), Refresh Token 테이블도 둔다. ②는 페이지 이동마다 재발급 요청이 한 번 더 생긴다.
