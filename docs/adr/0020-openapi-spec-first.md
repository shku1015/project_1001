# ADR-0020. API 명세는 openapi.yaml을 먼저 쓰는 방식(명세 우선)

- 상태: 승인
- 날짜: 2026-10-05
- 관련 문서: [06-api-spec.md](../06-api-spec.md), [08-architecture.md](../08-architecture.md) 2.1·8.2
- 바꾸는 결정: 08 문서의 "springdoc으로 코드에서 Swagger 생성(코드 우선)"

## 맥락

처음에는 API 문서를 코드에서 생성하는 **코드 우선** 방식으로 정했다. 하네스 엔지니어링 관점에서 다시 보니, 사람이 읽는 Markdown(06 문서)만으로는 에이전트가 "구현한 API가 명세와 같은지"를 자동으로 확인할 수 없다. 기계가 읽는 명세가 코드보다 먼저 있어야 그것을 기준으로 서버와 React를 검증할 수 있다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 코드 우선 (springdoc으로 생성) | 명세를 따로 쓸 필요 없음 | 명세가 코드를 따라가므로 "명세와 다르게 구현"을 잡을 수 없음. React 타입이 서버 구현 후에야 나옴 |
| **명세 우선 (`openapi.yaml`을 먼저 작성)** | 명세가 기준이 되어 서버 응답·React 타입을 자동 검증. 서버와 프론트를 동시에 시작 가능 | YAML 작성·유지 비용. Markdown(06)과 맞춰야 함 |

명세 우선 안에서 서버 쪽 적용 방식도 검토했다.

| 서버 적용 방식 | 장점 | 단점 |
|---|---|---|
| OpenAPI Generator로 컨트롤러 인터페이스·DTO 생성 | 컴파일 시점에 맞춤 | 공통 응답 틀(`{ success, data, error }`)을 제네릭으로 표현하기 어려워 응답마다 감싸는 타입이 생성됨. 전자정부프레임워크 컨트롤러 작성 방식과 거리가 생김 |
| **계약 테스트로 검증** (서버 코드는 직접 작성) | 컨트롤러·DTO를 자유롭게 작성. 실제 응답이 명세와 맞는지 테스트로 확인 | 테스트가 없는 API는 검증되지 않음 |

## 결정

- API의 요청·응답 형식은 **`api/openapi.yaml`이 정본**이다. API를 추가·변경할 때는 이 파일을 먼저 고친다.
- 06 Markdown 문서는 규약·업무 설명·화면 매핑을 담당하고, 필드 목록은 `openapi.yaml`을 따른다.
- 서버: 컨트롤러와 DTO는 직접 작성하고, 통합 테스트에서 **실제 요청·응답을 `openapi.yaml`로 검증**한다 (계약 테스트).
- React(①): `openapi.yaml`에서 **TypeScript 타입을 생성**해 쓴다. 생성 결과는 커밋한다.
- ② JSP + API: 타입 생성은 하지 않고, E2E 테스트로 확인한다.
- 개발 환경의 Swagger UI는 이 `openapi.yaml`을 그대로 보여 준다. 코드에서 명세를 생성하지 않는다.
- CI: `openapi.yaml` 문법·규칙 검사(lint), 서버 계약 테스트, React 생성 타입이 최신인지 확인을 추가한다. 이전에 계획한 `api-snapshot` 작업은 필요 없어져 뺀다.

## 결과

- 좋은 점: 에이전트가 "명세 수정 → 타입 생성 → 서버 구현 → 계약 테스트" 순서로 일하면, 명세와 다른 구현이 CI에서 바로 드러난다. 서버와 React 작업을 명세만 보고 동시에 시작할 수 있다.
- 감수할 점: `openapi.yaml`을 손으로 쓰고 유지해야 한다. 06 Markdown과 내용이 어긋나지 않게 관리해야 한다 (필드 상세는 YAML에만 두어 중복을 줄인다).
