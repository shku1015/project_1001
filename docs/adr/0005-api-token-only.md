# ADR-0005. REST API는 토큰으로만 인증

- 상태: 승인
- 날짜: 2026-10-04
- 관련 문서: [06-api-spec.md](../06-api-spec.md) 3절, [06-api/00-auth.md](../06-api/00-auth.md)

## 맥락

②를 세션으로 정했을 때는 "API가 세션과 토큰을 모두 받는다"고 적었다. ADR-0004에서 ②를 토큰으로 바꾸면서, API를 호출하는 프론트(①②)가 모두 토큰을 쓰게 되었다. ③은 API를 호출하지 않는다 (ADR-0003).

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| API가 세션·토큰 모두 허용 | 나중에 세션 클라이언트가 생겨도 대응 | 쓰지 않는 경로가 생기고, 세션 요청이면 API에도 CSRF 방어가 필요해짐 |
| **API는 토큰만** | 보안 설정이 경로별로 명확 (`/api/**` 토큰, `/ssr/**` 세션) | 세션으로 API를 부르는 클라이언트는 지원하지 않음 |

## 결정

- `/api/**`는 `Authorization: Bearer` 토큰으로만 인증한다. 로그인·재발급만 예외.
- Refresh Token 쿠키는 `/api/v1/auth/token` 경로에만 보낸다. 그래서 **로그아웃도 이 경로의 `DELETE /auth/token`** 으로 둔다 (쿠키가 함께 와야 토큰을 폐기할 수 있음).
- ③의 본문 이미지 업로드처럼 SSR 화면에서 필요한 비동기 요청은 `/ssr/**` 아래에 세션 인증 경로로 따로 둔다.

## 결과

- 좋은 점: API에는 CSRF 토큰이 필요 없다. 인증 실패 응답이 401 하나로 단순하다.
- 감수할 점: 같은 기능이 API와 SSR 경로에 각각 있어야 하는 경우(본문 이미지 업로드)가 생긴다.
