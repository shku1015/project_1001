# ADR-0003. 프론트 3종이 하나의 Service 계층을 공유

- 상태: 승인
- 날짜: 2026-10-04
- 관련 문서: [00-roadmap.md](../00-roadmap.md) 2절, [05-ia-screens.md](../05-ia-screens.md) 7절, [08-architecture.md](../08-architecture.md) 4절

## 맥락

학습 목적으로 같은 기능을 ① React + REST API, ② JSP + REST API, ③ JSP 서버 렌더링 세 가지로 만든다. 업무 규칙이 세 곳에 따로 구현되면 동작이 어긋나고 비교의 의미가 없어진다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| **Service 하나 + 진입점 둘** (`@RestController`, `@Controller`) | 업무 규칙·검증·오류 코드가 한 벌 | 컨트롤러가 두 종류로 늘어남 |
| ③도 내부에서 REST API를 호출 | 진입점이 하나 | 같은 서버 안에서 HTTP를 한 번 더 거침. SSR 학습 의미가 줄어듦 |
| 프론트마다 백엔드 따로 | 완전한 독립 | 업무 규칙 중복. 비교 대상이 달라짐 |

## 결정

- 업무 로직은 `admin-core`의 Service 하나에 둔다. ①②는 `@RestController`(API), ③은 `@Controller`(JSP)를 거쳐 같은 Service를 호출한다.
- ③은 REST API를 호출하지 않는다.
- 화면 명세는 프론트와 무관하게 **1벌**만 쓰고, API 명세는 ①②가 공통으로 쓴다.
- 오류 코드는 API·SSR이 같은 것을 쓴다 (API는 JSON, SSR은 화면 메시지).

## 결과

- 좋은 점: 세 프론트의 동작 차이는 화면 구현에서만 생긴다. 공통 E2E 시나리오 하나로 세 프론트를 검증할 수 있다.
- 감수할 점: Service가 "현재 관리자"를 인증 방식과 무관한 인터페이스로 받아야 한다. 화면 명세에 프론트별 구현 차이 표(05 문서 7절)를 따로 관리해야 한다.
